# FanPulse 项目闯关手册

这里不是“照抄教程”，而是一条由测试驱动的项目路线。仓库已经提供函数签名、测试、目录和设计文档；你负责补全实现、增加必要测试并记录自己的判断。完成 00～14 关后，会得到一个可运行、可部署、可观测、可压测的 FanPulse。

## 怎么使用

1. 一次只做一关，不要先改后续关卡的 TODO。
2. 阅读本关文档和引用的设计文档。
3. 先运行本关命令，确认测试因为预期原因失败。
4. 用最小实现让测试通过，再补边界测试和重构。
5. 运行 `go test -race`（涉及并发时必须）和此前所有关卡。
6. 在 GitHub Issue/PR 中记录实现、取舍和验证结果。

> 测试通过是进入下一关的必要条件，但不是充分条件。你还要能不用背稿解释“为什么这样设计”。

Windows PowerShell 中如果默认 Go 缓存没有写权限，可临时执行：

```powershell
$env:GOCACHE="$PWD/.cache/go-build"
```

## 测试命令规则

- 当前关：文档给出的精确 `go test` 命令。
- 回归：把已经通过的包一起测试，而不是直接运行尚未完成的所有关卡。
- 最终：`go test -race ./...`，再运行带 `integration` 标签的测试和 kind E2E。
- `coursechecks` 只验证必要工程产物，不验证实现质量；不要为通过字符串检查而写无效配置。

## 卡住时的顺序

1. 读失败消息，写下“期望、实际、最小复现”。
2. 只读函数注释、测试和相关设计章节。
3. 使用 `go test -run TestName -v` 缩小范围。
4. 使用 `go test -race`、日志、调试器或最小实验获取证据。
5. 仍然卡住时再查官方文档，并把答案用自己的话记入学习日志。

禁止通过删除断言、跳过测试、硬编码测试输入或让函数永远返回成功来“通关”。

## 每关提交建议

一个关卡可以有多个 commit，但最终用一个 PR 自审。推荐标题：`feat(course): complete level 03 event joining`。PR 中回答：我实现了什么？哪个不变量最重要？哪种失败最难排查？如果流量扩大 100 倍，哪里先成为瓶颈？
