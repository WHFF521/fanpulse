## 2. 背景与愿景

大型线上活动在开场、奖励开放和抽选报名时会出现突发流量。FanPulse 用一个虚构的 Creator 活动平台复现这些问题，并提供具备生产思维的解决方案。

项目的成功不以功能数量衡量，而以以下证据衡量：

- 在并发和重试条件下保持业务正确性。
- 对关键链路提供可解释的架构取舍与可复现实验。
- 能在本地以较低成本运行，并能演进至 Kubernetes 参考环境。
- 代码、部署、监控、测试和文档形成完整闭环。

## 3. 范围

### 3.1 产品角色

| 角色 | 职责与权限 |
| --- | --- |
| 访客 | 浏览公开活动信息 |
| 注册用户 | 预约活动、领取奖励、报名抽选、查看个人结果 |
| 运营管理员 | 创建/发布活动与奖励、发起抽选、查看任务状态 |
| 平台运维者 | 部署、观测、扩容、告警处置与故障演练 |

MVP 可以使用本地签发的 JWT 和种子账号，不实现完整 OAuth 登录页面。

### 3.2 核心范围

- 用户最小资料与认证主体映射。
- 活动列表、详情、发布状态和活动容量信息。
- 活动预约与重复预约的幂等响应。
- 限量奖励领取、库存控制和领取记录查询。
- 抽选报名、异步开奖任务、结果查询。
- Outbox 事件发布、消费者幂等、重试和死信处理。
- 用户级与全局限流。
- 健康检查、优雅停机、指标、日志、追踪。
- 本地开发、容器化、Kubernetes 部署和自动化测试。

### 3.3 暂不纳入

- 真实支付、商品订单、配送和退款。
- 聊天、直播推流、视频转码或 CDN 媒体分发。
- 真实邮件、短信、推送渠道；仅保留通知事件或模拟适配器。
- 完整前端和复杂内容管理系统。
- 多租户计费、跨地域多活和现实级灾备。
- 生物信息、真实艺人资料或版权素材。

## 4. 业务规则

| 编号 | 规则 |
| --- | --- |
| BR-001 | 同一用户对同一活动最多存在一条有效预约记录。 |
| BR-002 | 只有 `PUBLISHED` 且当前时间处于预约窗口内的活动可预约。 |
| BR-003 | 同一用户对同一奖励最多成功领取一次。 |
| BR-004 | 奖励成功领取总数不得超过 `total_quantity`。 |
| BR-005 | 相同 `Idempotency-Key` 与相同请求语义必须返回相同业务结果。 |
| BR-006 | 相同 `Idempotency-Key` 被不同请求载荷复用时返回冲突。 |
| BR-007 | 只有已预约活动的用户可领取该活动奖励或报名抽选。 |
| BR-008 | 抽选报名在截止后不可新增；每个用户每场抽选最多一条报名。 |
| BR-009 | 开奖任务状态只允许按 `PENDING -> RUNNING -> COMPLETED/FAILED` 转移。 |
| BR-010 | 同一个消息事件即使被重复投递，业务副作用也只发生一次。 |
| BR-011 | 管理操作必须通过管理员身份鉴权并记录审计字段。 |

## 5. 功能需求

优先级采用 MoSCoW：Must、Should、Could、Won't（当前路线内不做）。

### 5.1 用户与活动

| 编号 | 优先级 | 验收标准 |
| --- | --- | --- |
| FR-001 | Must | 用户可创建演示账号，邮箱规范化后保持唯一。 |
| FR-002 | Must | 访客可分页查询已发布活动并按状态过滤。 |
| FR-003 | Must | 用户可查询单个已发布活动的时间、状态和奖励摘要。 |
| FR-004 | Must | 合法用户可预约开放中的活动；重复调用返回已有记录而非新增记录。 |

### 5.2 奖励

| 编号 | 优先级 | 验收标准 |
| --- | --- | --- |
| FR-101 | Must | 用户携带 `Idempotency-Key` 发起领取；缺少该头返回 400。 |
| FR-102 | Must | 并发领取后成功数不超过库存，库存不出现负数。 |
| FR-103 | Must | 用户重试成功请求时获得相同领取 ID 和状态。 |
| FR-104 | Must | 库存耗尽返回明确的业务错误，不重试扣减。 |
| FR-105 | Should | Redis 路径可原子检查重复、检查库存并扣减；数据库唯一约束仍是最终保护。 |
| FR-106 | Must | 用户可分页查询自己已领取的奖励。 |

### 5.3 抽选与异步处理

| 编号 | 优先级 | 验收标准 |
| --- | --- | --- |
| FR-201 | Must | 合格用户可在报名窗口内报名抽选，重复报名不新增。 |
| FR-202 | Must | 管理员发起开奖后立即获得任务 ID，HTTP 状态为 202。 |
| FR-203 | Must | Worker 分批处理报名者，生成不超过名额的唯一中奖结果。 |
| FR-204 | Must | 任务可查询状态、处理数量、错误摘要和完成时间。 |
| FR-205 | Should | 临时失败按指数退避重试，超过阈值进入 DLQ 并产生指标。 |

### 5.4 平台能力

| 编号 | 优先级 | 验收标准 |
| --- | --- | --- |
| FR-301 | Must | `/health/live` 反映进程存活；依赖故障不应直接判定进程死亡。 |
| FR-302 | Must | `/health/ready` 在关键依赖不可用或排空期间返回 503。 |
| FR-303 | Must | 收到 SIGTERM 后先退出就绪状态，停止接收新流量并在宽限期内处理在途请求。 |
| FR-304 | Must | API 输出 RED 指标，Worker 输出处理量、失败量和消费延迟指标。 |
| FR-305 | Must | 日志为结构化 JSON，并关联 `request_id`、`trace_id` 和服务名。 |
| FR-306 | Should | 用户级限流返回 429 与 `Retry-After`，并记录拒绝指标。 |

## 6. 非功能需求

### 6.1 正确性与一致性

- PostgreSQL 是业务事实源；Redis 可丢失的数据必须能重建或核对。
- 预约、奖励领取和抽选报名使用唯一约束兜底。
- DB 业务写入与领域事件写入使用同一事务的 Outbox 模式。
- Kafka 使用至少一次投递，消费者通过 `processed_events` 实现幂等。

### 6.2 性能目标

以下是验收目标，不是已测结果：

| 场景 | 本地参考目标 | 约束 |
| --- | --- | --- |
| 活动读取 | P95 < 150 ms | 1,000 虚拟用户、缓存预热 |
| 奖励领取 | P95 < 300 ms | 1,000 并发，包含成功与库存耗尽响应 |
| 错误率 | < 1% | 不含预期的 409、422、429 |
| 正确性 | 0 超发、0 重复权益 | 任意压测规模均为硬约束 |

每次结果必须记录硬件、容器资源、数据集、拓扑、脚本、Git 提交与时间。未达成目标时保留真实结果和瓶颈分析。

### 6.3 可用性与恢复

- Kubernetes 参考部署中 API 至少 2 个副本，滚动升级期间保持服务。
- API 不在本地内存保存跨请求业务状态，允许水平扩展。
- 可恢复消息失败不得静默丢失；重试耗尽后进入 DLQ。
- 为数据库迁移定义回滚或前向修复策略；破坏性迁移分阶段发布。

### 6.4 安全与隐私

- 所有非健康检查的写接口必须认证；管理员接口必须授权。
- 配置和密钥不提交到 Git；Kubernetes Secret 仅作为注入接口，生产参考采用外部密钥系统。
- 参数化 SQL、防止越权访问、请求体大小限制与输入校验必须启用。
- 日志不记录密码、Authorization、完整邮箱或原始 Idempotency-Key。
- CI 执行依赖、静态分析与容器镜像扫描。

### 6.5 可维护性

- Go 公共 API 有注释；核心领域逻辑有单元测试，存储和并发路径有集成测试。
- OpenAPI、迁移和配置示例纳入版本控制。
- 关键架构取舍写入 `docs/adr/`；文档与实现变更在同一 PR 中提交。

## 7. 用例与验收场景

### UC-01 重试预约

1. 用户首次预约成功，获得参与记录 ID。
2. 客户端因响应丢失再次发送相同业务请求。
3. 系统返回同一参与记录，数据库仍只有一行。

### UC-02 奖励抢领

1. 创建库存 100 的奖励和至少 1,000 个合格用户。
2. 1,000 个用户并发领取，部分客户端主动重试。
3. 断言成功记录恰好 100 条、每用户至多一条、剩余库存为 0。

### UC-03 消费者崩溃恢复

1. Worker 完成数据库写入但在提交 Kafka offset 前终止。
2. Worker 重启并重新收到同一事件。
3. `processed_events` 唯一约束阻止重复副作用，消息最终被确认。

### UC-04 Kubernetes 排空

1. 向 API 持续发送请求并触发 Pod 终止。
2. Pod 先变为 not ready，不再获得新请求。
3. 在途请求在宽限期内完成，未观察到非预期 5xx 峰值。

## 8. 迭代与完成定义

### 8.1 产品待办顺序

- M1：FR-001～004、FR-301～303。
- M2：FR-101～104、FR-106 和奖励并发验收。
- M3：FR-105、FR-306 和性能基线。

- M5：Kubernetes、可观测性与 CI/CD。
- M6：负载报告、故障实验、ADR 和项目展示材料。

### 8.2 每个 Issue 的完成定义

- 验收标准满足，异常路径有覆盖。
- `go test ./...`、lint 和相关集成测试通过。
- API、迁移、配置或部署变化已同步文档。
- 无新增高危扫描项，无密钥进入历史。
- PR 描述包含验证证据；单人项目也必须自审 diff 后合并。

## 9. 假设、风险与开放决策

| 项目 | 当前结论 |
| --- | --- |
| 消息组件 | 采用 Kafka 以展示通用企业能力；本地开发控制为单节点。 |
| 初始服务形态 | 模块化单体 API + Worker，而非多个同步微服务。 |
| 云平台 | 本地 kind 为主；AWS EKS 仅作参考架构，避免持续费用。 |
| 前端 | 非核心，优先 OpenAPI/Swagger 与脚本化演示。 |
| 许可证 | 首个可运行版本前确定，暂定 Apache-2.0。 |
| 最大风险 | 技术栈过宽导致功能未闭环；通过里程碑和明确非目标控制。 |
